> 覆盖周期：2026-07-20 至 2026-07-26  
> 数据来源：仓库内 `daily/2026/07/2026-07-20.md` 至 `2026-07-23.md`。7 月 24 日至 26 日未发现对应 daily 文件，因此本报告仅基于仓库中实际存在的上一周简报汇总。

## 一、本周核心判断

**企业 AI 的主战场正在从模型能力和问答效果，迁移到 Agent 的运行时控制、业务语义和行动治理。**

本周多条线索指向同一个架构变化：数据库厂商开始把 Agent 身份、权限、协议和审计下沉到数据层；云厂商开始像管理微服务一样监控 Agent 会话和资源；模型厂商开始向企业软件和交付服务延伸；图数据库与本体则获得了新的战略位置——连接跨系统身份、数据、工具、规则、业务对象和行动证据，形成企业 Agent 的全局关系控制层。

更清晰的企业 AI 分工正在形成：

- **模型**负责理解、推理和计划生成；
- **Agent**负责调用工具和执行任务；
- **数据库与业务系统**负责本地权限、事务和强制执行；
- **本体**负责统一业务概念、规则、动作与约束；
- **图数据库**负责跨系统关系、状态、影响、权限传播和证据链；
- **治理平台**负责观测、审批、审计、停止、回滚与责任追踪。

这意味着，图数据库不应只把自己定位为 GraphRAG 的检索组件，而应升级为 **Enterprise Context Graph 与 Agent Governance Graph 的运行基础设施**。

## 二、Weekly｜本周趋势总结

### 1. 数据库进入 Agent 原生阶段，争夺数据访问控制点

EDB 将 Agent 身份、声明用途、权限和企业策略组合为受约束的 PostgreSQL 请求，并复用角色、行级安全与会话审计执行控制。Oracle 则把 A2A 服务嵌入 Autonomous AI Database，使外部 Agent 可以发现并调用数据库内 Agent。

这表明数据库厂商不再满足于“被 Agent 查询”，而是希望成为 Agent 网络中的可信执行节点。数据库天然适合在表、行、事务和会话层面执行强约束，但单个数据库难以理解跨 CRM、ERP、湖仓、文件、模型服务和外部 API 组合形成的完整业务动作。

因此，更合理的产品架构不是“图数据库替代所有数据库”，而是：

1. 数据库和业务系统负责本地强制执行；
2. 图数据库和本体负责全局关系治理；
3. Agent 控制平面负责跨系统计划、审批、观测和证据归档。

参考：[EDB Agentic Database](https://www.enterprisedb.com/press-releases/edb-launches-agentic-database-converged-analytics-and-governance-bringing-sovereign)、[Oracle Autonomous AI Database A2A Server](https://blogs.oracle.com/developers/introducing-oracle-autonomous-ai-database-a2a-server-for-governed-multi-agent-systems)。

### 2. Agent 可观测性从附加功能变成生产基础设施

AWS Bedrock AgentCore 新增 `ActiveSessionCount` 指标，说明 Agent 已经被视为需要容量管理、配额、告警和成本治理的新型运行时负载。

企业未来不仅要观察接口延迟和服务错误，还要观察：

- Agent 活跃会话与并发；
- 工具调用链和失败重试；
- 数据、模型与提示词版本；
- 单任务资源和成本消耗；
- 行动影响范围与异常中断；
- 谁授权、谁审批、谁承担责任。

这为图数据库提供了一个清晰入口：将用户、Agent、角色、工具、数据、模型、规则、任务、证据和风险事件建模为一张持续更新的运行治理图。

参考：[Amazon Bedrock AgentCore Release Notes](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/release-notes.html)。

### 3. Context Graph 成为图数据库面向 Agent 的新叙事

《Context Graphs for Proactive Enterprise Agents》提出用实时关系结构表达企业实体、关系、当前状态和状态变化，使 Agent 不再只是被动回答问题，而能主动发现变化、识别影响对象并触发行动。

传统知识图谱主要回答“世界是什么样”，Context Graph 进一步回答：

- 现在发生了什么变化；
- 变化影响了谁；
- 哪些规则被触发；
- 下一步可以或不可以执行什么动作；
- 需要通知、审批或补偿哪些主体。

这一方向把 GraphRAG、Agent Memory、数字孪生、事件驱动和治理能力连接到同一套图模型中。对图数据库厂商而言，Context Graph 比单纯宣传知识图谱或向量检索更接近企业的真实预算和生产需求。

参考：[Context Graphs for Proactive Enterprise Agents](https://arxiv.org/abs/2607.07721)。

### 4. GraphRAG 从“提升召回”转向“上下文工程与证据治理”

《Is GraphRAG Needed?》提醒行业：更复杂的检索结构并不必然带来等比例的生成质量提升，检索指标改善与最终回答质量之间存在“检索—生成落差”。

GraphRAG 的长期价值不应只建立在“召回更准”上，而应体现在：

- 上下文结构化和可裁剪；
- 多跳证据与路径可解释；
- 权限、时间和版本可约束；
- 证据来源和业务口径可审计；
- Agent 能基于结构化证据继续执行。

因此，GraphRAG 产品需要同时评估回答质量、token 成本、证据完整度、路径可信度和治理可用性，而不是只展示向量相似度或召回率。

参考：[Is GraphRAG Needed?](https://arxiv.org/abs/2606.25656)。

### 5. 图与向量融合进入工程优化阶段

Neo4j 2026.06.0 引入高保真量化向量搜索预览，通过量化候选搜索和全精度重排降低内存消耗并保持召回质量。这说明图数据库的向量竞争已经从“是否支持”转向生产工程能力：内存、吞吐、过滤下推、二阶段重排、混合代价估算和冷热分层。

专用图数据库更应强调 **Graph-guided Vector Search**：

- 先用业务关系、本体类别、权限或时间范围缩小候选集，再做向量检索；
- 或先由向量发现候选实体，再用路径、规则、关系强度和风险传播重排。

这比把 HNSW 简单嵌入图数据库更能体现图与独立向量库的差异。

参考：[Neo4j Release Notes](https://neo4j.com/release-notes/)、[Neo4j Vector Indexes](https://www.neo4j.com/docs/cypher-manual/25/indexes/semantic-indexes/vector-indexes/)。

### 6. PostgreSQL SQL/PGQ 将扩大图查询市场，也提高专用图数据库门槛

PostgreSQL 19 Beta 2 继续推进 SQL/PGQ 属性图能力。主流关系数据库吸收图查询，会使客户更频繁地问“为什么不能直接使用 PostgreSQL”。

专用图数据库不应否认 SQL/PGQ，而应明确分层：

- SQL/PGQ 让关系数据获得标准化图查询入口；
- 专用图数据库面向大规模多跳遍历、复杂路径、图算法、实时关系计算、分布式图存储、GraphRAG 和 Agent 治理。

SQL/PGQ 会扩大图技术市场教育，但专用产品必须用数量级性能、生产稳定性和业务语义能力证明不可替代性。

参考：[PostgreSQL 19 Beta 2 Released](https://www.postgresql.org/about/news/postgresql-19-beta-2-released-3350/)。

### 7. OpenAI 向企业软件与高接触交付延伸

本周 daily 收录的报道显示，OpenAI 正通过企业软件、实施服务、模拟、护栏、人类审核和 Agent 评估，向企业工作流更深处延伸。其产业含义是：模型 API 的价值会受到价格竞争与开源模型挤压，企业客户真正愿意持续付费的是可控地嵌入业务流程并取得结果。

对图数据库和本体厂商而言，机会不在于再做一层通用聊天界面，而在于提供模型厂商难以独立完成的企业语义、复杂关系、权限传播、影响分析和证据链。

参考：[OpenAI Presence 报道](https://www.businessinsider.com/openai-presence-corporate-software-customer-service-sales-2026-7)、[OpenAI 企业交付战略报道](https://www.wsj.com/cio-journal/openais-high-stakes-high-touch-push-to-make-ai-work-for-business-7f08b7d4)。

## 三、Monthly｜月度趋势演进

截至 2026 年 7 月下旬，本月趋势已经从“Agent 应用快速增加”进一步演进为“Agent 控制权下沉与分层治理”。

### 本月新增判断

1. **数据层治理与全局关系治理将并存。** 数据库负责本地强制执行，图与本体负责跨系统整体合法性判断。
2. **Context Graph 将成为知识图谱的新一代产品表达。** 重点从静态知识转向状态、变化、影响和行动上下文。
3. **Agent 可观测性正在成为独立基础设施层。** 会话、调用链、成本、异常和影响范围都需要统一度量。
4. **本体开始承担运行时政策角色。** 概念和关系之外，还要定义动作、前置条件、审批要求和证据义务。
5. **GraphRAG 的竞争重心转向上下文成本和治理能力。** 单纯提高召回率不足以建立长期壁垒。

## 四、Topics｜专题知识沉淀

### Graph Database

图数据库的新定位应从“复杂关系查询引擎”扩展为：

> 企业 Agent 的上下文状态层、关系推理层和行动证据层。

建议重点建设：

- Context Graph 参考模型；
- Agent Governance Graph；
- Graph-guided Vector Search；
- 图查询与向量查询统一代价分析；
- 时间、版本、权限与证据路径；
- 事件驱动的状态变化和影响传播。

### AI Agent

Agent Control Plane 至少需要统一管理：

- Agent 身份、所有者、用途和风险等级；
- 用户委托、角色继承和临时授权；
- 工具、API、数据和模型访问边界；
- 任务计划、会话、资源与成本；
- 规则命中、审批、执行和回滚；
- 证据、业务影响和责任链。

### Data Governance & Ontology

本体应从知识描述升级为机器可执行的业务政策层，明确：

- 哪类主体可以对哪类对象执行哪些动作；
- 动作需要满足哪些前置条件；
- 哪些数据在何种上下文下可访问；
- 哪些操作必须人工审批；
- 哪些结论必须保留证据；
- 规则冲突时采用 permit、review 还是 deny。

### FinTech

金融行业的关键不是“部署聊天机器人”，而是构建可信执行链。优先场景包括：

- 监管报送规则发现、预审核与影响分析；
- 授信审查中的企业、实控人、司法和舆情关联；
- 反洗钱中的账户、交易、设备、地址与受益人网络；
- 模型、特征、规则、审批和业务结果的全链路治理；
- 高风险 Agent 的分级授权、人工确认和补偿回滚。

## 六、Papers｜论文与技术文章

### Context Graphs for Proactive Enterprise Agents

- 链接：[arXiv:2607.07721](https://arxiv.org/abs/2607.07721)
- 核心贡献：使用实时关系结构表达实体、关系和状态变化，使 Agent 能主动发现变化和相关影响。
- 产业意义：连接知识图谱、事件驱动、数字孪生、Agent Memory 和行动治理。

### Is GraphRAG Needed? From Basic RAG to Graph-/Agentic Solutions with Context Optimization

- 链接：[arXiv:2606.25656](https://arxiv.org/abs/2606.25656)

- 产业意义：GraphRAG 产品必须关注上下文工程、token 成本、证据质量和生产治理。

### Agentic GraphRAG: Navigating Unstructured Financial Data with Collaborative AI

- 链接：[arXiv:2605.18770](https://arxiv.org/abs/2605.18770)
- 核心贡献：将结构化强节点、非结构化弱节点、实体解析、协作 Agent 和图工具结合。
- 产业意义：适用于工商、司法、监管、财报、舆情和供应链等多源金融数据。

## 七、对悦数的工作建议

### 1. 统一产品叙事

建议将图数据库、本体、AskGraph、MCP、GraphRAG 和图算法统一到一个更高层定位：

> **悦数图是企业 Agent 的关系与语义基础设施。**

### 2. 建设三项优先能力

1. **Agent Control Graph**：统一建模用户、Agent、工具、数据、规则、任务、行动、证据和影响。
2. **Ontology-driven Tools**：根据本体和政策生成受约束的工具参数和动作接口。
3. **Agent Dry Run**：执行前模拟权限、规则、后续影响和潜在冲突，输出 permit、review 或 deny。

### 3. 构建 Context Graph 样板场景

优先选择监管报送、授信风险或供应链风险，展示：

> 数据变化 → 关系影响 → 规则判断 → Agent 建议或行动 → 审批 → 执行 → 证据归档

### 4. 强化图与向量差异化

不要只强调支持向量索引，应重点展示图约束候选裁剪、关系重排、权限过滤、路径证据和混合查询成本分析。

### 5. 面对 PostgreSQL SQL/PGQ 的标准话术

> SQL/PGQ 推动图查询普及；专用图数据库则解决复杂关系智能的生产问题，包括大规模多跳遍历、路径分析、图算法、实时关系计算、GraphRAG 和 Agent 治理。
